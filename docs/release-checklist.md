# Проверка перед выпуском

Дата: 29 октября 2026. Формат текущей версии — общее демо без авторизации.

## Выполненные проверки

- `npm test`: тест API-клиента, production-сборка frontend, сборка backend и интеграционные тесты на отдельной SQLite-базе.
- `npm run typecheck`: frontend и backend.
- `npm run build:hosting`: сборка с PostgreSQL-клиентом; использован фиктивный адрес, подключение к Neon не выполнялось.
- `prisma validate --schema backend/prisma/postgres/schema.prisma`: PostgreSQL-схема корректна.
- Модели SQLite и PostgreSQL совпадают; для всех пяти этапов есть миграции обоих провайдеров. SQLite SQL выполняется интеграционным тестом. SQL PostgreSQL в новой реальной базе в этом прогоне не запускался.

Чистая установка `npm ci` в этом прогоне не подтверждена: Windows блокировала файл работающего preview-сервера, затем скачивание пакетов задержалось. Preview был остановлен, локальные зависимости и исполняемые ссылки восстановлены; заключительные тесты выполнялись с восстановленным окружением. Перед `npm ci` на Windows останавливайте серверы проекта. Проверка чистой установки остаётся пунктом финальной приёмки.

Интеграционный тест проверяет доски, списки, карточки и чек-листы: создание, чтение, изменения, удаление, каскадное удаление, изоляцию вложенных маршрутов, ограничения длины, даты, отметки выполнения, перенос и порядок. После перезапуска повторно проверяются сохранённые записи. В production-режиме проверяются `/api/health`, API и прямое открытие маршрута доски.

API-клиент проверяется на JSON-ошибках, ответе 502 с HTML, некорректном успешном ответе, сетевой ошибке и отсутствии повторной отправки записи. Ожидание чтения увеличено до 90 секунд для пробуждения Render, записи — до 30 секунд. При потере ответа запись могла сохраниться: сначала следует обновить страницу и проверить результат.

## Зависимости и ограничения

Prisma обновлена до 6.19.3; multer закреплён на 2.5.0 через корневой override. Полный аудит после пересчёта lock-файла: 3 high (Prisma CLI / @prisma/config / deepmerge-ts) и 3 low (Nest CLI / fork-ts-checker-webpack-plugin / deepmerge). Обновление инструментов с переходом основных версий остаётся техническим долгом перед выпуском, если требуется полностью чистый аудит. Инструменты используются на хостинге при сборке и миграциях; отсутствие пользовательского пути к их функциям не означает отсутствия предупреждений.

`npm ls` в локальном npm 11.6.2 помечает multer 2.5.0 как `invalid` относительно точной зависимости 2.4.0, объявленной NestJS. В корневом manifest задан override, lock-файл и установленный пакет содержат 2.5.0, тесты с ней проходят. До финального выпуска нужно подтвердить чистую установку с override в окружении сборки; успешный прогон тестов не заменяет эту проверку.

Персональные доски не реализованы: посетители общего демо имеют доступ к общим данным. Авторизация и права доступа требуют отдельного этапа.

## Финальная ручная приёмка

1. Запустить `npm run dev`, создать доску и три списка.
2. Создать, переименовать и переместить карточки мышью, стрелками и через меню. Обновить страницу и сверить порядок.
3. Проверить описание, срок, отметку выполнения и все действия с чек-листом.
4. Проверить поиск по названию и описанию, фильтры выполнения и просрочки, сброс поиска.
5. Проверить отмену форм и подтверждений по Escape, возврат фокуса, пустые состояния и ошибки.
6. На настоящем телефоне проверить свайпы, перетаскивание, экранную клавиатуру и доступность кнопок. Проверка размеров окна не заменяет проверку касаний.
7. Удалить только специально созданные проверочные данные; убедиться, что непустой список удалить нельзя.
8. После отдельно разрешённого деплоя повторить основные действия на хостинге и проверить сохранение после обновления страницы.

Коммит, push и деплой выполняются только по отдельной команде пользователя. Этот прогон не изменяет рабочие данные и Neon.
